# AGENTS.md

Not a code project, with one exception: `manager/` is a stdlib-only Python control plane over the recipes. Otherwise this is a workspace of **independent VPN server deployment recipes**, each a Chinese runbook plus a re-runnable `setup-*.sh`. No build, test, lint, or package manifest anywhere — do not invent commands.

## Version control & backups
- Git repo, branch `main` (baseline `71b7add`); **no remote configured** (`git remote -v` empty) — don't push. `.gitignore` keeps private keys, PSKs and runtime state out; **no private keys are in history** (only public CA/client certs and the deliberate default-`test` `VPNC/clients/vpnc.conf`). Never `git add -f` ignored files.
- `tools/backup.sh` tars the whole workspace (including the gitignored secrets and `.git`) to `$BACKUP_DIR` (default `~/vpn-backups`), emits `.sha256` + a `.txt` manifest, and keeps the last `KEEP` (default 14: set `KEEP=N`). `tools/restore.sh <archive.tar.gz> [--yes]` overlays it back. Run backup before risky changes; the archive is 0600 because it contains live keys.

- Read the matching `*使用指南.md` before changing a deployment; scripts and docs assume it.
- Run each `setup-*.sh` as the normal user, **not** via `sudo`: every script self-elevates with an internal `$SUDO` (`sudo` when not root). Running it as root makes `$SUDO` empty and leaves generated PKI/clients root-owned (strongSwan only chowns back when it saw `sudo`).
- `openvpn/AGENTS.md` holds deeper OpenVPN-only gotchas (Docker static install, EasyRSA quirks, encrypted-key/secret-agent issue). Keep OpenVPN facts there, don't duplicate here.
- `可用VPN/可用VPN/` is vendored **upstream** Docker build trees (2023–2024), reference only: dirs `vpn-l2tp`, `vpn-pptp-no-mppe`, `vpn-openvpn-tls`, `vpn-openconnect-cert` (plus client `wh-vpn-linux-tcp.conf` and an `安装指导.txt`). The live recipes above were adapted from these; to change `openvpn/` or `OpenConnect/`, edit their `setup-*.sh`, not these trees. Don't confuse the upstream container names (e.g. `running-vpn-l2tp`, `running-vpn-openvpn-tls`) with the live containers in the table.
- `Agent.md` (singular) is a dated Chinese work-summary; this `AGENTS.md` is the stable instruction file. `VPN连接失败排查方法.md` is the layered troubleshooting guide (port conflicts, `sg docker`, IP/cert changes, and the client-side connectivity test method in §7).
- Default credentials: username/password VPNs use `test`/`test` (L2TP_PLAIN, PPTP, VPNC; OpenVPN client `client` + encrypted-key passphrase `test`). strongSwan and OpenConnect are certificate-only. `L2TP_IPSEC/vpn.env` is **gitignored and not committed** (current working tree: `test`/`test` + a random PSK); `setup-l2tp.sh` only creates it (`l2tpuser` + random PSK/password) when absent, so deleting it rotates the L2TP/IPsec creds.
- Only `openvpn/setup-openvpn.sh` installs Docker (apt → Tsinghua static binaries → registry mirror). `L2TP_IPSEC`, `Strongswan`, `PPTP`, `OpenConnect`, and `VPNC` `die` if Docker is missing/not running — install it via the OpenVPN script first. `L2TP_PLAIN` is host-only and needs no Docker (it only probes running containers when present).
- `L2TP_IPSEC/docker-compose.yml` is an unused alternative to `setup-l2tp.sh`; it lacks the post-start `ike=` patch, so use the script.

## Unified manager (`manager/`)
- Thin control plane over all 7 recipes; it **never edits them** — only reads status and calls `docker`/`systemctl`/`ss`/`openssl`. The recipe dirs + `setup-*.sh` stay authoritative; to change a deployment edit those, not the manager. See `manager/README.md`.
- Stdlib-only Python 3, no deps/tests. **Needs Python ≥3.11** (imports stdlib `tomllib` for the protocol TOMLs; host runs 3.12). `vpnctl` is a symlink to `vpnctl.py`; run from inside `manager/` (`vpnctl.py` does `import store`, `web.py` does `import vpnctl`, so the manager dir must be on `sys.path`).
- Keys are hyphenated and differ from dir names: `openvpn` `l2tp-ipsec` `l2tp-plain` `strongswan` `pptp` `openconnect` `vpnc`. Commands: `list` (`--json`), `status <key>` (`--json`), `info <key>`, `logs <key> --tail N`, `clients <key>` (per-protocol connected-client evidence), `raw <key>`, `ip`, `doctor`, plus persistence: `events [<key>]`, `audit`, `collect` (standalone log collector), `prune`, `health`, `alerts`, `watch` (`--once`/`--interval`) — all with `--tail`/`--json` where relevant.
- **Persistence/observability:** `manager/store.py` is a SQLite store at `<repo>/state/vpnplat.db` (state/ is gitignored; override via `VPNCTL_STATE_DIR`/`VPNCTL_DB`): `events` (matched connection events) + `audit` (every `up/down/restart/enable/disable` with actor/source/ok/duration). `manager/collector.py` follows each protocol's `docker logs -f`/`journalctl -f`, writes matched lines to the DB and **all** lines to `state/logs/<key>.jsonl` (5MB x3 rotation), and prunes periodically. `web.py` starts it automatically (guarded by `state/collector.lock`; `--no-collect` disables); web actions record `source=web` + client IP as actor.
- **Health/watchdog (P3):** `manager/health.py` checks per-service status/ports plus IP-bound cert expiry (`openssl -enddate`) and cert CN/SAN vs current IP; `manager/watchdog.py` polls it (default 30s from `config/platform.toml`, override with `VPNCTL_CONFIG`) and alerts via `manager/notify.py` (always to DB `alerts`; desktop `notify-send` + optional `alerts.webhook`, gated by `alerts.min_level`). It alerts on status transitions, server-IP drift, cert expiry (once/day), running-but-port-not-listening, and can auto-restart only `failed` services (`health.auto_restart`, audit `source=watchdog`). Available as `vpnctl watch [--once|--interval N]` or embedded in `web.py` (auto-start, `state/watchdog.lock`, `--no-watch`); endpoints `/api/health`/`/api/alerts`.
- **Single source of truth:** protocol metadata lives in the **repo-root** `config/protocols/<key>.toml` (not `manager/config/`; `vpnctl.ROOT` resolves it) (`order`/`key`/`title`/`kind`/`target`/`ports`/`group`/`subnet`/`gateway`/`client`/`docs`/`verify`/`note`/`client_hint`/`log_events`/`cert_check` + `[[probes]]` and `[[clients_cmds]]` tables). `vpnctl.py:_load_protocols()` loads them at import via stdlib `tomllib` and builds `VPN_DEFS`/`VPN_BY_KEY`/`LOG_EVENTS`/`CERT_CHECKS`; `web.py` consumes those. Add or change a VPN by editing its TOML, not the Python.
- Lifecycle: `up`/`restart`/`enable` auto-stop conflicts; `down` only stops; `enable`/`disable` also toggle autostart (`docker --restart=unless-stopped|no`, `systemctl enable|disable`).
- `up`/`restart` auto-stop the other `ipsec500` members (`strongswan`/`l2tp-ipsec`/`vpnc`); `--keep-conflicts` skips that. `doctor` reports docker-access mode, group conflicts, and whether the IP-bound certs (strongSwan/OpenConnect) match the current IP.
- `web.py` binds `127.0.0.1:8787`; **writes need no token by default** (open on localhost); `--auth` re-enables the token (`manager/.token`, auto-generated 0600, or `VPNCTL_TOKEN` env) sent as `X-VPNCTL-Token`. Flags: `--read-only`, `--auth`, `--no-auth` (legacy no-op), `--token`, `--host/--port`, `--no-collect`, `--no-watch`, `--no-open`. Never expose publicly; remote via `ssh -L 8787:127.0.0.1:8787`. UI is a dashboard: dark left sidebar (数据看板 overview + one page per VPN); overview has stat cards/bars/table plus 最近告警/最近操作 cards (from `/api/alerts`/`/api/audit`, and a red banner if `/api/health` reports problems); per-VPN pages have tabs 状态概览/配置信息/实时日志/历史事件 (log tab pulls `docker logs`/`journalctl` and highlights per-protocol connection events via `vpnctl.LOG_EVENTS`, polls every 2s; history tab reads persisted events from `/api/events`). `/api/health` is TTL-cached ~5s so the 4s overview poll stays cheap. The overview re-renders only when a status/IP signature (`ovSig()`) changes and updates 最近告警/最近操作 in place (cached `OV_EXTRA`), so auto-refresh does not flicker — keep that behavior when editing the UI. Per-VPN prefs (`autoStop`→`keep_conflicts`, `tail`, `scope`, `live`) live in browser `localStorage`, not on disk. Endpoints `/api/list|detail|raw|clients|logs|stream|events|audit|health|alerts` (logs tab uses SSE `/api/stream`) + POST `/api/action` (`up`/`down`/`restart`/`enable`/`disable`, optional `keep_conflicts` bool, or a `name`-less bulk/admin action: `down-all` stops every running VPN; `clear-alerts` deletes only alerts whose problem is already resolved, keeping active ones — the active set comes from `watchdog.active_alert_titles()`, so a still-broken cert/service alert cannot be cleared).
- Quick launch: `manager/panel-open.sh` opens `http://127.0.0.1:8787/` in the browser (starts the systemd service via `pkexec`, else backgrounds `python3 web.py`; log at `state/panel-open.log`). `python3 web.py` itself also auto-opens it when a graphics session exists (`--no-open` disables; the systemd installer passes it). `VPNCTL_HOST`/`VPNCTL_PORT` override. The dashboard boots into 数据看板 (`overview`), not the first VPN. If 8787 is already held by the enabled `vpn-manager-web` service, `web.py` prints bind-conflict guidance (service already running, open the URL, how to stop it) instead of a traceback.
- Docker access is auto-detected as `plain`/`sudo -n`/`sg docker`/none; `l2tp-plain` is the host `xl2tpd.service` (SysV-wrapped): mutating ops and journal reads need root, so `vpnctl.systemctl()`/`vpnctl._journalctl()` try `sudo -n` then fall back to a direct call; `sudo manager/install-sudoers.sh` grants NOPASSWD for `systemctl start|stop|restart|enable|disable|is-active|status xl2tpd` and `journalctl -u xl2tpd` only (everything else still needs the password). SysV units ignore `systemctl --now`, so `enable` = enable+start and `disable` = stop+disable explicitly. `install-web-service.sh` generates `/etc/systemd/system/vpn-manager-web.service` from `SUDO_USER`/`HERE`/`python3` (needs sudo); the checked-in `systemd/vpn-manager-web.service` is an unused hardcoded reference (user `uos`) — edit the installer, not the unit.

## Cross-cutting gotchas
- **Port conflict (500/4500/udp):** `Strongswan/`, `L2TP_IPSEC/`, and `VPNC/` all need 500/4500/udp — pick one. `setup-strongswan.sh` auto-stops `ipsec-vpn-server`; `setup-vpnc.sh` auto-stops both `strongswan-server` and `ipsec-vpn-server`. Switch back with `docker start <container>`. OpenVPN, L2TP_PLAIN, PPTP, and OpenConnect coexist with any.
- **UDP 1701 overlap:** `L2TP_PLAIN` (host `xl2tpd`) and `L2TP_IPSEC`'s inner L2TP both use 1701. If an L2TP/IPsec client's first L2TP packet arrives before IPsec is up, the host `xl2tpd` answers it and the client gets a `192.168.44.x` (plain-L2TP) address instead of `192.168.42.x`; reconnect fixes it. Stop `xl2tpd` to remove the ambiguity. Verified both UOS V20 (strongSwan 5.7.2) and V25 (strongSwan 6.0.1) connect to L2TP/IPsec with default client config after the server `ike=` fix below.
- **Server IP:** all scripts accept `SERVER_IP=<ip>`, else auto-detect via `ip route get 1.1.1.1`; behind NAT pass the public IP explicitly. OpenVPN/L2TP certs are IP-independent, but **strongSwan and OpenConnect server certs embed the IP in the cert** (strongSwan: CN+SAN; OpenConnect: **SAN only** — `setup-openconnect.sh:30` defaults `CERT_CN` from `SERVER_IP` before the IP is auto-detected, so running it without `SERVER_IP=...` yields an empty CN). Health compares the current IP against **both CN and SAN IP entries** (`vpnctl.cert_matches_ip`), so a SAN-only cert is correctly `OK`, not a false mismatch. `setup-strongswan.sh` auto-detects an IP mismatch and re-issues **only the server cert**; `setup-openconnect.sh` re-signs the server cert every run (CA + client certs kept). Delete `Strongswan/pki/` only to rotate the CA. The host's WiFi IP is DHCP and drifts (observed `10.20.50.203 → 10.20.51.22 → 10.20.50.132 → 10.20.8.90`) — confirm the current IP before editing client configs; clients pointing at a stale IP receive nothing. `vpnctl doctor`/`health` flags a cert/IP mismatch; re-run the relevant `setup-*.sh` (with `SERVER_IP=` if auto-detect is wrong) to re-sign.
- **strongSwan IKEv2 client gotchas (GUI/NetworkManager):** (1) server must set `rightsendcert=always` — otherwise it sends no `CERTREQ` in IKE_SA_INIT and NM clients (`leftsendcert=ifasked`) never send their cert → `AUTH_FAILED` / `no trusted RSA public key found for 'CN=client1'`; (2) client must check "请求内网 IP" (`virtual=yes`), else server rejects with `FAILED_CP_REQUIRED`/`TS_UNACCEPT` and no `10.10.10.x`; (3) server cert must match the current IP. Verified both UOS V20 (NM-strongswan 1.4.4) and V25 (1.6.0) connect via GUI. FAQ in `Strongswan/客户端连接方法.md` §10.
- Scripts are idempotent but the build-based ones (OpenVPN/strongSwan/PPTP/OpenConnect/VPNC) **rewrite their own generated artifacts** (`Dockerfile`, `entrypoint.sh`, `etc/*.conf`) and rebuild the image on every run; OpenVPN/L2TP/strongSwan reuse existing PKI, OpenConnect re-signs only the server cert. Edit the `setup-*.sh` heredocs, not the generated files.
- **L2TP/IPsec IKE proposal:** hwdsl2's default `ike=` stops at MODP2048. UOS **V20** (strongSwan 5.7.2) defaults to `MODP3072` first, giving `NO_PROPOSAL_CHOSEN` ("VPN认证失败"); UOS **V25** (strongSwan 6.0.1) defaults to `MODP2048` and works as-is. `setup-l2tp.sh` now appends MODP3072/4096 + `dh19/dh20/dh21/dh31` to the container's `/etc/ipsec.conf` after start and restarts ipsec, covering both. Do **not** add `modp1024` — Libreswan 5.4 rejects the whole `ike=` line and `l2tp-psk` silently fails to load (only `ikev2-cp` remains). Verify with `docker exec ipsec-vpn-server ipsec status | grep 'Total IPsec connections'` (expect `loaded 3`). Client-side key is `ipsec-ike`/`ipsec-esp` on both V20 and V25 (not `phase1-algs`). Details in `L2TP_IPSEC/UOS_V20_V25客户端差异总结.md` and `VPN连接失败排查方法.md` §2.1.
- **L2TP/IPsec MPPE:** the server pppd has `noccp` (no CCP, so no MPPE). Clients must **not** enable "使用 MPPE 点到点加密". UOS V25's NM-l2tp 1.20.20 drops `noccp` and adds `require-mppe` when MPPE is checked → `pppd: MPPE required...` and disconnect; UOS V20's NM-l2tp 1.2.10 always writes `noccp` so it connects either way. Verified in `L2TP_IPSEC/UOS_V20_V25客户端差异总结.md` §3.
- **PPTP:** needs `--net host --privileged` (Docker bridge can't forward GRE proto 47). In `etc/pptpd.conf`, `remoteip` range must use the last-octet form (`192.168.45.10-250`); writing `192.168.45.10-192.168.45.250` makes pptpd try to DNS-resolve it and exit 1 (crash-loop). MPPE defaults to `require-mppe-128` (`MPPE=no ./setup-pptp.sh` disables it). Coexists with all other VPNs (unique ports). Verified V20/V25 connect and route via `ppp0`.
- **OpenConnect (ocserv):** needs `/dev/net/tun` + `--privileged`; bridge + `-p 8443:8443/tcp -p 8443:8443/udp`. **Certificate auth** (`auth = "certificate"`, `cert-user-oid = 2.5.4.3` → login name = client cert CN): CA + server (CN/SAN=IP) + client certs under `etc/ocserv/`; client fills CA=`ca.crt`, 用户证书/私钥=`client.crt`/`client.key`, no password. Coexists with all (8443). `setup-openconnect.sh` re-signs the server cert each run (CA + client cert reused; it still generates a vestigial `ocpasswd`, and its header comment wrongly says plain `test/test` — trust the generated `ocserv.conf`, auth is certificate). Verified V20 GUI + CLI → `vpn0`/`tun0=192.168.46.x`, DTLS up, internet OK. Gotcha: V20 `dde-daemon`'s VPN secret agent can wedge (`failed to createPendingKey`) so NM never launches openconnect; **log out/in** resets it (keyring itself is fine). Details in `OpenConnect/OpenConnect使用指南.md` §2/§5.
- **VPNC (Cisco IPSec):** IKEv1 Aggressive + PSK + XAUTH + MODECFG, container `vpnc-server` (`--net host --privileged`), port 500/4500/udp. strongSwan 5.8+ **disables Aggressive Mode + PSK by default** — the image ships `/etc/strongswan.d/vpnc.conf` with `i_dont_care_about_security_and_use_aggressive_mode_psk = yes`; without it the client gets `ISAKMP_N_INVALID_EXCHANGE_TYPE` and the server logs `Aggressive Mode PSK disabled for security reasons`. Client (`vpnc`, at `/usr/sbin/vpnc` — not in a non-login PATH) needs `IPSec gateway/ID/secret` + `Xauth username/password` in a config file (secret/password are config-file-only). No pingable tunnel gateway (mode-config); verify by internet access. Verified UOS V20 (10.20.9.40) CLI + GUI → `tun0=192.168.47.x`, internet OK. Details in `VPNC/VPNC使用指南.md`.
- Live secrets live in-tree but are **`.gitignore`d** (never in git history): `L2TP_IPSEC/vpn.env`, `openvpn/local-server/clients/`, `Strongswan/{pki,clients}/`, `PPTP/etc/ppp/chap-secrets`, `OpenConnect/etc/ocserv/*.key`, `VPNC/etc/ipsec.secrets` + `VPNC/clients/`, plus the runtime `manager/.token` (web write token, 0600). Never paste contents into logs or external services; `vpnctl info` is deliberately secret-free. A fresh clone therefore cannot run until secrets are restored from `tools/backup.sh` output.

## Host environment (UOS)
- Docker: `uos` is now in the `docker` group, so **new** shells (and opencode's) call `docker` directly — `vpnctl` detects this as `plain`. Only a long-lived shell opened before the group add needs `sg docker -c '...'` or `sudo docker ...`; don't add `sudo` when direct access works. Docker was installed from Tsinghua **static binaries** into `/usr/local/bin` because the UOS apt CDN is hijacked; registry mirror `https://docker.m.daocloud.io` is set in `/etc/docker/daemon.json`.
- UOS AppArmor blocks strongSwan client certs under `$HOME`: put `ca.crt`/`client*.crt`/`client*.key` in `/etc/ipsec.d/`.
- UOS `pppd` 2.4.9 rejects `lock`/`local`/`proxyarp` (already removed from `L2TP_PLAIN` options). EasyRSA 3.1.7 rejects `EASYRSA_REQ_CN` for `build-server-full`/`build-client-full` (CN comes from filename); only `build-ca` accepts it.
- Containers use `--restart unless-stopped`: after a manual `docker stop`, a reboot will **not** bring the VPN back until `docker start`.

## Verification (no test suite)
- OpenVPN: `docker logs --tail 20 running-vpn-openvpn-tls | grep "Initialization Sequence Completed"`, `ss -ulnp | grep 1194`
- L2TP/IPsec: `docker exec ipsec-vpn-server ipsec status` / `ipsec trafficstatus`
- L2TP_PLAIN: `systemctl status xl2tpd`, `ss -ulnp | grep 1701`
- strongSwan: `docker exec strongswan-server ipsec statusall` (look for `ikev2-cert`)
- PPTP: `docker ps --filter name=pptp-server`, `ss -tlnp | grep 1723`, `docker exec pptp-server ps -ef | grep pptpd`
- OpenConnect: `docker ps --filter name=openconnect-server`, `ss -tlnp | grep 8443`, `docker exec openconnect-server occtl show status`
- VPNC: `docker ps --filter name=vpnc-server`, `docker exec vpnc-server ipsec statusall` (look for `cisco-vpnc`), `docker exec vpnc-server cat /var/log/charon.log`
- Client side: `ip -4 addr show <tun0|ppp0>` then ping the gateway `.1` (e.g. `10.99.99.1`, `192.168.42.1`).
- Fastest overview: `cd manager && ./vpnctl list` / `./vpnctl doctor` (works in this env — docker is auto-detected as `plain`).
